## Feature backlog

- **Harness recovery (requested 2026-10-14).** Today a stopped agent harness (rollout, eviction, SIGTERM) is retried once from scratch in a fresh container (`HARNESS_INTERRUPTED`, r20), so the agent loses its in-progress work and conversation. Goal: resume a stopped harness from its last checkpoint: recover the uncaptured workspace edits, replay the transcript/session into the restarted harness, and re-attach to the same task revision without a duplicate capture or a second budget reservation. Also: graceful drain on planned rollouts (finish or checkpoint running attempts before replacing instances).
- **Cross-run file claims.** Concurrent runs should see which files another run is editing (task, agent, feature) so agents coordinate before colliding, instead of discovering overlaps only at merge time.
- **Server-side guided autopilot.** Autopilot currently runs from the open guide tab; move stage advancement to the server so it continues with the tab closed.
- **Live agent activity feed.** During a run, "View logs" shows only model-call timing; the agent's tool calls, files touched and reasoning appear only in the transcript after it finishes. Stream tool-call and file events while the agent works.
- **Reasoning level control.** Let the owner set reasoning effort per role (planner, specialist, integrator, coordinator) in the guide and team runs, or choose "agents decide" so each agent raises effort only for hard steps. Tonight the guided demo pins every role to low effort; before that, an unset effort meant the provider default (maximum thinking for GLM), which made each turn take 5–20 s.
- **Retry agents after a container-state reset.** On 2026-10-15 00:45:09 UTC Cloudflare reset an `ExecutionContainer` Durable Object ("Internal error in Durable Object storage caused object to be reset"); two seconds later the git proxy could not resolve the attempt's scope and returned 409, failing the integrator. Classify that failure as retryable (like `HARNESS_INTERRUPTED`) and restore the attempt scope after a reset. The git proxy now logs the failing stage (`git_proxy.failed`).
- **Reject and fix.** Review offers two choices: Reject (recorded with a reason, nothing ships) and Reject and fix (the owner writes what to change; an agent applies that request to the rejected result on the same working branch, fresh checks run, and the revised result is shown again as the new Agents' pick, with the rejected one kept in history). Builds on `reject_candidate` and the existing continuation/repair flow.
