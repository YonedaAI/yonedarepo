# Build, compare and publish a website

Open the platform and choose **Sign in**, or **Create account** with a username or email and password. Use the same registered identifier for sign-in and recovery. An email identifier is not automatically linked to an existing username account; registering it creates a separate account. Email verification and email-based password recovery are not implemented. Save the one-time recovery code privately. The header shows your registered username or email after authentication; its account menu provides **Sign out**. **Administrator access** is a separate operator-token flow. No owner token is required for a personal workspace.

1. Choose **Connect Agents** in the sidebar. Connect a hosted provider or your own repository-scoped MCP/Git agent. Provider keys are encrypted on the server and never returned to the browser. The reviewer account already has managed model connections; no key setup is required.
2. Choose **New repository**. Start with the template or import a public HTTPS Git repository containing an initial commit. Setup runs in the background; its stage, errors and retry action remain visible.
3. Choose **Start a Run** and describe what to build, add or fix. **Build together** starts with one Auto preference; YonedaRepo can plan complementary agents from the approved connected pool. Optional rows contain model, role and supported reasoning effort. Task ownership and dependencies are system responsibilities.
4. For independent alternatives, choose **Compare two approaches**. It uses two builders and a separate Auto reviewer. You approve the brief once; builders, review and up to two repairs share bounded funding under the workspace allowance. Opening a form or choosing a sample starts no inference. Billing and credits are not required for this demo.
5. Builders work from the same frozen source and context. Each result is captured and independently checked. In Compare, checks alone never advance the working head: the read-only reviewer waits for both terminal builder results, compares them against intent, prior context, exact source and checks, then records a recommendation and reasons for both alternatives.
6. If neither approach meets the goal, the reviewer may request a repair of the more promising captured alternative. Every repair needs fresh capture, checks and review, with at most two repair rounds. Exhaustion or unresolved evidence produces **Needs attention**, not a forced winner. Model retries do not renew the logical review allowance.
7. Review the selected output, its explanation, checks and unresolved risks. **Review changes** lets you choose files individually. Both alternatives remain inspectable. **Use other result** records your reason and updates only the checked working selection, guarded against source, policy and version changes. The original agent review is retained unchanged.
8. Choose **Publish result** when the checked working result meets your goal. Confirm the intent; an optional human note supplements the stored agent explanation without replacing it. Publication is a separate human decision. The publisher checks ancestry, uses an expected-old Git lease and reads back the canonical commit before the serving pointer advances.

Existing two-builder runs have **Review now**. Its confirmation approves review plus up to two repairs of the retained source, without restarting the original builders. It creates a separate immutable funding segment and retains original usage, reservations and approvals. Older one-to-six-builder runs still allow guarded manual selection; they do not invent an automatic review.

Compare reviewers can inspect frozen evidence and submit an assessment; they cannot edit source, delegate, request capture or publish. Agent explanations are assertions. Source capture and independent checks establish different evidence; choosing a working result does not publish it. Preview links remain one-hour bearer capabilities.

Use **Restart run** to reopen a finished or cancelled run's brief, root agents, context and budgets.
Review the settings and approve to create a fresh run on the current canonical source. Usage starts
at zero; the old run's failures, candidates and decisions remain available in run history. Active
work must finish or be cancelled first. Missing or changed provider connections require an explicit
choice before approval; restarting never silently changes a model or charges for an automatic retry.

Static output must contain `index.html` in the approved `static_dir`, at most 500 regular files and 8 MiB decoded content. Symlinks and unsafe paths fail capture. Use relative asset URLs; for Vite, set `base: './'`. Sites are served on a separate Worker origin with an opaque browser sandbox and no platform credentials. Arbitrary external API calls, service workers and server-side application hosting are outside this static profile.

Use **Context graph** search and type filters to find prior assertions, then expand a selected record's relationships. **Source history** traces an exact source revision/path to the decision, alternatives and evidence. A follow-up run can select previous records in its brief, preserving the context it actually received.

The workflow engine owns scheduling, capture, evaluation and publication. Agents supply code and typed context; their completion signal requests capture, rather than approval. The owner makes the shipping decision in the website. External MCP credentials deliberately have no selection or publication tool. Typed questions are currently recorded context: an interactive clarification request that pauses and resumes an attempt is a future workflow capability, not implemented by chat prompts outside the product.

## Update a published website

Choose **Update website** (or **Update project** for a source-only release), describe the change and approve a new run. Its base is the current canonical published source revision, shown in the form; the currently hosted revision is shown separately if it differs. The form restores the winning published agent's connection, model and exact approach, including custom instructions. It suggests one agent; add or remove agents or choose a different connection before approval. Initial builds suggest two alternatives, with the same editable roster.

The **Continuing your published work** panel identifies the prior brief and revision and lets you inspect its approach and shipping decision. Its acceptance criteria and winning model's configured limits are prefilled, with fresh usage. Current repository checks still apply. The **Reuse existing context** selection carries the published decision, original intent, candidate, evaluation and available artifacts/findings from the winning agent's lineage and shared research. These are explicit, editable references, bounded to 50 records; findings remain assertions. Competing agents' new assertions are not automatically selected. If a connection was removed or changed model, choose a replacement explicitly. Missing historical details fall back to preserving the current design instead of inventing a previous model.

Completed agents remain visible as history; publication does not restart them. A new run freezes its own brief, source, selected context, agents and budgets. Its `continuation_of` references the verified published decision, and the graph records a **continues** edge. **View published base** opens the preceding run. If another publication wins while the form is open, the server rejects its stale lineage before scheduling work; refresh and review the updated brief. A newer failed or unpublished run does not become the update's base.

Review the captured change and independent checks, then select and publish it through the same workflow. With one agent, no alternative comparison is required. The existing website keeps serving until the new publication is verified. Active runs retain their approved roster; use a new run to change membership. **Restart run** remains a separate action for retrying a historical brief and root roster on current source.

## Delete a repository

Select the repository, open **Repository options (⋯)** beside the header refresh button, then choose **Delete repository**. Type the exact repository name and confirm. Failed imports and repositories still provisioning can also be deleted. The console selects another repository or returns to the empty workspace.

Deletion is permanent in the product: the repository ID cannot be reused or restored. It blocks new runs, MCP/Git access, stale callbacks, published pages and previously issued preview links. Active jobs are fenced in the same ledger transaction; container stops, workspace discovery updates, key revocation and managed Git cleanup use a durable retrying outbox. A response lost after deletion can be retried safely. Late provisioning and capture cannot revive the repository. Background sweeps also remove managed imports or forks that finish after the original request ends; these checks back off from one minute to daily.

Shared provider connections and other repositories remain available. Managed personal Git repositories and their captured/contribution forks are scheduled for deletion through the [Artifacts binding](https://developers.cloudflare.com/artifacts/api/workers-binding/#deletename). Legacy administrator repositories may reference shared Git sources, which are retained. Internal audit/ledger records and content-addressed R2 evidence are retained and inaccessible through the deleted repository; deletion is not a promise to erase every stored byte. Shared evidence requires separate reference-aware retention management.

# Local operation

`cargo xtask setup` creates private local authentication and vault keys. `cargo xtask dev` runs the platform at `http://localhost:8787` and the sites Worker at `http://localhost:8788`. Local Durable Objects, D1 and R2 use `.wrangler/state`; Artifacts uses the configured remote development namespace and requires Cloudflare authentication. Hosted inference is paid when you approve a run; `cargo xtask check` launches none.

After deployment, run `cargo xtask seed-template --url URL` once as the platform operator. It creates the small Artifacts starter using a short-lived Git capability and revokes that capability. Personal project creation then forks the starter through the browser. This operator bootstrap is separate from user onboarding.

Cloudflare supports separate dev commands when [each Worker needs its own local URL](https://developers.cloudflare.com/workers/local-development/multi-workers/). The developer command manages both processes. Source tests and local browser checks do not establish successful deployed inference, Artifacts capture, publication or hosting; those are recorded separately in the release evidence.
